Gym CRM QA Showcase

The agent read the Gym CRM requirements (business rules BR-101 to BR-702, acceptance criteria AC-01 to AC-30, roles and permissions), judged which criteria are testable, drafted cited test cases, and ran approved tests in a real browser against a separate copy of Gym CRM with its fictional Demo Gym data. Verdicts come only from code assertions; every suggestion from the AI is labeled as one.

AI: keyless stand-in. Readiness verdicts, drafts and triage suggestions below come from a simple deterministic heuristic, not a model, so read them as pipeline output, not AI judgment. Browser verdicts, safety gates and findings do not depend on the AI. A run with live Claude replaces these results.

What the showcase found

In the agent (found and fixed during this showcase)

  • Test results depended on the machine's language Fixed

    The executor did not pin a browser locale, so Gym CRM rendered its login page in Vietnamese on one machine and English on another, and the same spec failed on one of them. The executor now pins en-US by default (configurable), with a test.

  • A redirect could make a passing test inconclusive Fixed

    Gym CRM redirects /finance to /finance/payments on the client at an unpredictable moment after load. The screenshot taken after the navigation step sometimes raced it (3 of 25 runs). Navigation screenshots are now supporting evidence: if one cannot be captured, the step log says why and the run continues. Assertion screenshots stay mandatory. After the fix: 0 inconclusive runs in 50.

  • Redaction mangled secret names in reproduction notes Fixed

    The reproduction write-up showed the password step as [secret:[REDACTED] because the redactor treated the reference name as a value. The secret was never exposed. References of the exact form [secret:NAME] are now kept; real values in brackets are still redacted. Test added.

  • Locators could not scope Gym CRM's dropdowns Fixed

    Gym CRM uses custom dropdowns (a listbox of options) and only a main landmark on some pages. The allowed ARIA roles gained main, listbox and option. No new step type was added (ADR-0008).

  • Large requirement sections overflowed the context budget Fixed in the source preparation

    With whole business-rule sections as sources, 28 of 30 criteria hit the 1,800-token budget and the agent refused them rather than truncating. Sources now hold one block per rule (BR-xxx) and per permission row. Six long criteria still exceed it; the agent asks for them to be split.

About Gym CRM

  • AC-04 is enforced on the server Confirmed

    Saving a lead with channel "Khác" and no note is refused by the server, not only by the form: the field shows "Đã chọn \"Khác\" thì phải ghi rõ" and a toast reports invalid data.

  • Sign-in is rate limited Observation

    25 sign-ins within about a minute produced HTTP 429 for some attempts. This is brute-force protection working; it means test suites should sign in once per role and reuse the session.

  • The sidebar is not a navigation landmark Accessibility

    The main menu has no <nav> element, ARIA navigation role or test ids, so assistive technology cannot jump to it and tests cannot scope menu links to it. The trainer check therefore asserts that "Tài chính" appears nowhere on the page.

  • Two channel dropdowns on one page Observation

    The leads page has a "Kênh liên hệ" filter and a "Kênh liên hệ" field in the add-lead dialog. Page-wide locators would be ambiguous; every step is scoped to its dialog.

"Refused" and "BLOCKED" are the expected, safe outcomes here. The destructive run never started; it waits for a QA lead's approval tied to that exact action and environment.

Triage of a staged failure

All real tests passed, so one test was run with a deliberately wrong expectation to show what happens on failure. STAGED

FAILEDverdict, from the assertion (ASSERTION_FAILED:staged-wrong-expectation)
PRODUCT_DEFECTsuggested cause (stand-in heuristic); the true cause is a test issue

The suggestion is wrong, and that is the point of the design: a suggested cause never changes the verdict, and nothing is filed in Jira until a person confirms the cause and a QA lead approves the filing.
