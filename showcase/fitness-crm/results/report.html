Gym CRM QA Showcase

A 30-case regression suite for the Gym CRM sample, built and run with the Manual QA AI Agent. Every case traces to a requirement in the Gym CRM docs. The agent drafted the cases, a QA engineer revised them and a QA lead approved them. 17 cases have executable steps, approved by a second person, and run in a real browser against a separate copy of Gym CRM with its fictional Demo Gym data. Verdicts come only from code assertions.

AI: keyless stand-in. Drafts, readiness verdicts and triage suggestions come from a simple deterministic heuristic, not a model. Browser verdicts, the suite, the safety gates and the timing figures do not depend on the AI. A live Claude run will replace the AI parts.

One-time cost of automation

Writing the 17 executable specs (exploring the UI, choosing locators, debugging) is a real cost that this showcase did not time. At 51 min saved per weekly run it pays back after spec hours ÷ 0.84 h weeks: at 30 min per spec (8.5 h) after about 11 weeks, at 60 min per spec after about 21 weeks. Keeping specs current when the UI changes comes on top.

Where the agent helps

  • The same verdict every run: both suite runs gave identical results, with no tester fatigue.
  • Evidence for every case: screenshots at each assertion, step and network logs, with secrets masked.
  • Traceability from requirement to case to run result, kept automatically.
  • Unsafe actions are stopped by policy, not by memory (4 of 4 here).
  • Requirement gaps surface before testing starts.

Where people are still needed

  • 13 of 30 cases stay manual: date-relative booking flows, contract creation, money arithmetic.
  • Reviewing and approving every case and every executable (the second-person rule).
  • Exploratory testing and visual or usability judgement, which the agent does not attempt.
  • Confirming failure causes: the agent's suggestion was wrong on the staged failure.
  • Preparing sources and keeping specs current when the UI changes.

Findings

In the agent

  • Keyword retrieval blocks narrow permission questions open

    For 3 of 30 cases (TC-05, TC-08, TC-09) and 5 of 31 requirement stories, full-text retrieval matched 15 to 20 loosely related permission rows, because role names and words like "permission" appear throughout the permissions document. The total exceeded the 1,800-token budget and the agent refused instead of truncating approved sources, even after the statement was narrowed. Refusing is the safe behavior, but it blocks drafting. Recommendation: rank by relevance and keep exact-ID matches plus the strongest hits within the budget (vector ranking, deferred in ADR-0005), as a reviewed design change.

  • Test results depended on the machine's language fixed

    The executor did not pin a browser locale, so Gym CRM rendered its login page in Vietnamese on one machine and English on another, and the same spec failed on one of them. The executor now pins en-US by default (configurable), with a test.

  • A redirect could make a passing test inconclusive fixed

    Gym CRM redirects /finance to /finance/payments on the client at an unpredictable moment after load. The screenshot taken after the navigation step sometimes raced it (3 of 25 runs). Navigation screenshots are now supporting evidence: if one cannot be captured, the step log says why and the run continues. Assertion screenshots stay mandatory. After the fix: 0 inconclusive runs in 50.

  • Redaction mangled secret names in reproduction notes fixed

    The reproduction write-up showed the password step as [secret:[REDACTED] because the redactor treated the reference name as a value. The secret was never exposed. References of the exact form [secret:NAME] are now kept; real values in brackets are still redacted. Test added.

  • Locators could not reach Gym CRM's dropdowns and dialogs fixed

    Gym CRM uses custom dropdowns (a listbox of options), a main landmark, and an alert dialog for the duplicate-phone warning. The allowed ARIA roles gained main, listbox, option and alertdialog. No new step type was added (ADR-0008).

  • No test suites added

    The agent managed single cases and runs only. It now has test suites: named sets of cases in sections, run together, with a suite-run report of per-case verdicts, durations, evidence and traceability (migration 0005, API, tests). Manual and unapproved cases are listed in every run, never counted as passed.

  • Failure text and matching use different views of the page open

    expectText matches an element's text content, but a failure reports its rendered text. On Gym CRM the two differ ("Còn lại21" versus "Còn lại" and "21" on separate lines; amounts end in a non-breaking space before ₫), which made one assertion harder to write. Worth documenting or reporting both views.

  • Sources needed careful preparation done in the source preparation

    Whole business-rule sections overflowed the budget (28 of 30 criteria refused), so sources hold one block per rule and per permission row, the latter restated as "granted to" lists. Preparing sources is part of the setup cost.

About Gym CRM

  • All 17 automated checks pass, twice confirmed

    Sign-in and access per role, lead rules (AC-04, AC-25, BR-202), the Kanban board, locked and derived contract values (BR-305, BR-602) and expired contracts behave as the requirements say, in two consecutive runs.

  • AC-04 is enforced on the server confirmed

    Saving a lead with channel "Khác" and no note is refused by the server, not only by the form: the field shows "Đã chọn \"Khác\" thì phải ghi rõ" and a toast reports invalid data.

  • Duplicate phones get a clear merge prompt confirmed

    Entering an existing customer's phone opens "Số điện thoại đã có hồ sơ", names the record (KH000001 · Nguyễn Văn An) and offers "Gộp vào hồ sơ này" or "Quay lại sửa".

  • Sign-in is rate limited observation

    Gym CRM allows 20 sign-ins per minute per IP, by design. Back-to-back suite runs hit it (sign-in returned HTTP 429), so runs are spaced a minute apart. Reusing one session per role would remove the wait.

  • The sidebar is not a navigation landmark accessibility

    The main menu has no <nav> element, ARIA navigation role or test ids, so assistive technology cannot jump to it and tests cannot scope menu links to it.

  • The demo data's draft contract is approved demo data

    The demo seed describes Bùi Thanh Tâm's contract (HD000008) as "a draft, not activated yet", but it shows "Đang hiệu lực", approved by Admin, likely because the seed approves every pending request afterwards. The demo therefore has no pending contract for booking tests.

Method and limits

  • Target: a separate Gym CRM instance (its own database and ports), seeded with pnpm db:seed:demo. The developer's own instance was not touched.
  • Sources: Gym CRM docs 05 (business rules), 14 (acceptance criteria) and 09 (roles), word for word, one block per rule; permission rows restated as "granted to" lists.
  • Cases and executable steps were written by Claude Code acting as the QA engineer, checked against the real UI, and approved in the agent by a different user acting as QA lead.
  • Each automated case signs in through the login page; the password is passed by reference and masked in screenshots. The browser locale is pinned to en-US.
  • 107 AI decisions and 55,640 tokens were recorded (counted by the stand-in; nothing billed).
  • Not covered: phone layouts, emails, check-in machines, reports other than the cash book case, and anything that needs a live model.
