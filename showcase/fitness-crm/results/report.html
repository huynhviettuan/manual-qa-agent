Gym CRM QA Showcase

Gym CRM full regression: 261 test cases covering every documented Gym CRM module, designed with 7 manual test-design techniques and traced to 96 requirements in the Gym CRM docs. The agent drafted each case from approved sources, QA revised it and a QA lead approved it. 131 cases run in a real browser against a separate copy of Gym CRM with its fictional Demo Gym data; verdicts come only from code assertions. The rest are managed as manual cases with the reason they are not automated.

AI: keyless stand-in. Drafts, readiness verdicts and triage suggestions come from a simple deterministic heuristic, not a model. Test design, browser verdicts, the suite, the safety gates and the timing do not depend on the AI. A live Claude run will replace the AI parts.

Findings

About Gym CRM

  • Price preview shows a raw English validation message (CON-07) defect

    Found by boundary-value analysis on the contract form. Typing 1001 sessions makes the live price panel show "Too big: expected number to be <=1000", an untranslated developer message, in the Vietnamese UI. Gym CRM's own catalog has the right text ("Nhập một số nguyên từ 1 đến 1000."), which the form does show on save, and 0 shows the normal placeholder. Low severity: nothing is saved. Reproduced in both suite runs.

  • The not-found page has two main landmarks (SEC-01) accessibility

    Opening a record id that does not exist renders one <main> nested inside another, both holding "Không tìm thấy". A page should have a single main landmark for assistive technology. The automated check came back INCONCLUSIVE because its strict locator refused to guess between them; asserting the "Không tìm thấy" heading instead would let it run.

  • 128 of 130 automated checks pass, identically in two runs confirmed

    Sign-in, every page of the permission matrix (60 checks across 30 pages and 6 roles, all matching docs/09), lead validation and boundaries, duplicates, search, customer standings, contract pricing boundaries, locked and derived contract values, finance access and API refusals behave as the requirements say.

  • Two definitions of "ending soon" requirement inconsistency

    The customer badge "Sắp hết hạn" follows decision A-131: only the end date (within 30 days). The dashboard's "contracts ending soon" uses 30 days or 3 sessions or fewer, and the demo seed calls a customer with 2 sessions left "ending soon". Both behave as their own rule says, but the two rules disagree; worth a product owner decision.

  • The sign-in limit is not "20 per minute" configuration risk

    Gym CRM configures Better Auth with 20 sign-ins per 60 seconds per IP, and its comment says the limit must let a whole shift sign in from the gym's one shared IP. Better Auth (1.7.7) resets the counter only after 60 seconds without a successful sign-in, and every successful sign-in restarts that wait. So after 20 sign-ins with gaps under a minute, everyone behind the gym's IP is refused (HTTP 429) until a full quiet minute passes. Observed: blocks after 20 sign-ins at about 11 per minute. Worth a sliding window or a higher limit for the shared IP.

  • AC-04 is enforced on the server confirmed

    Saving a lead with channel "Khác" and no note is refused by the server, not only by the form: the field shows "Đã chọn \"Khác\" thì phải ghi rõ" and a toast reports invalid data.

  • Duplicate phones get a clear merge prompt confirmed

    Entering an existing customer's phone opens "Số điện thoại đã có hồ sơ", names the record (KH000001 · Nguyễn Văn An) and offers "Gộp vào hồ sơ này" or "Quay lại sửa".

  • The sidebar is not a navigation landmark accessibility

    The main menu has no <nav> element, ARIA navigation role or test ids, so assistive technology cannot jump to it and tests cannot scope menu links to it.

  • The demo data's draft contract is approved demo data

    The demo seed describes Bùi Thanh Tâm's contract (HD000008) as "a draft, not activated yet", but it shows "Đang hiệu lực", approved by Admin, likely because the seed approves every pending request afterwards. The demo therefore has no pending contract for booking tests.

In the agent

  • Keyword retrieval refused 40% of a large suite fixed (adr-0010)

    With the full 261-case suite, 109 cases were refused because loosely related permission rows (matched only by shared keywords) did not fit the context budget, even though the requirement each story names did. The budget now keeps every exact-ID match and drops lower-ranked keyword-only matches with a recorded gap (ADR-0010, with a test). Drafted cases rose from 152 to 216 with the same sources; the evaluation gates still pass.

  • The functional requirements were missing from the sources fixed in the source preparation

    27 cases cite functional requirements (FR-LEAD-006, FR-CUS-003, …) from Gym CRM's 06_FUNCTIONAL_REQUIREMENTS.md, which was not loaded. The agent correctly refused them ("unsupported" or "no trusted context") instead of inventing support. Adding the document (76 FR rules, one block each) brought drafted cases to 259 of 261.

  • Test results depended on the machine's language fixed

    The executor did not pin a browser locale, so Gym CRM rendered its login page in Vietnamese on one machine and English on another, and the same spec failed on one of them. The executor now pins en-US by default (configurable), with a test.

  • A redirect could make a passing test inconclusive fixed

    Gym CRM redirects /finance to /finance/payments on the client at an unpredictable moment after load. The screenshot taken after the navigation step sometimes raced it (3 of 25 runs). Navigation screenshots are now supporting evidence: if one cannot be captured, the step log says why and the run continues. Assertion screenshots stay mandatory. After the fix: 0 inconclusive runs in 50.

  • Redaction mangled secret names in reproduction notes fixed

    The reproduction write-up showed the password step as [secret:[REDACTED] because the redactor treated the reference name as a value. The secret was never exposed. References of the exact form [secret:NAME] are now kept; real values in brackets are still redacted. Test added.

  • Locators could not reach Gym CRM's dropdowns and dialogs fixed

    Gym CRM uses custom dropdowns (a listbox of options), a main landmark, and an alert dialog for the duplicate-phone warning. The allowed ARIA roles gained main, listbox, option and alertdialog. No new step type was added (ADR-0008).

  • No test suites added

    The agent managed single cases and runs only. It now has test suites: named sets of cases in sections, run together, with a suite-run report of per-case verdicts, durations, evidence and traceability (migration 0005, API, tests). Manual and unapproved cases are listed in every run, never counted as passed.

  • Failure text and matching use different views of the page open

    expectText matches an element's text content, but a failure reports its rendered text. On Gym CRM the two differ ("Còn lại21" versus "Còn lại" and "21" on separate lines; amounts end in a non-breaking space before ₫), which made one assertion harder to write. Worth documenting or reporting both views.

  • Sources needed careful preparation done in the source preparation

    Whole business-rule sections overflowed the budget (28 of 30 criteria refused), so sources hold one block per rule and per permission row, the latter restated as "granted to" lists. Preparing sources is part of the setup cost.

Method and limits

  • Target: a separate Gym CRM instance (own database and ports), seeded with pnpm db:seed:demo; the developer's own instance was not touched.
  • Expected results come from the Gym CRM requirements (docs 05, 06, 09, 14 and decisions), not from the product's behaviour. Where they disagreed, the code was read before calling it a defect.
  • Valid boundary values on the lead form are checked without saving (the form is submitted without a channel, so only the channel error may appear), so reruns never collide with earlier data.
  • Cases and executable steps were written by Claude Code acting as the QA engineer and approved in the agent by a different user acting as QA lead. Browser locale pinned to en-US.
  • 584 AI decisions and 303,680 tokens recorded (counted by the stand-in; nothing billed).
